# T12 notes — camel-hump matching for members in `jdoc find`

Status: done. `./mvnw -B -Djdoc.buildDir=target/T12 verify` passes (whole tree, 105 ITs, all unit tests).
The tree was briefly uncompilable mid-way because of T13's in-progress `SqliteIndexStore` change; I waited.

## API changes
- `index.MemberRepository` / `JdbcMemberRepository`:
  - `listNames(artifactIds, subsequence)` → `List<String>` — distinct (case-sensitive) member names in scope whose
    name contains the characters of `subsequence` in order (`LIKE '%o%E%T%'`, ASCII case-insensitive, other chars
    exact); `""` lists every name. No order guaranteed.
  - `findByNames(names, artifactIds, limit)` → `List<IndexedMember>` — rows whose name equals one of `names`
    (case-sensitive), usual order (type binary name, artifact id, declaration), `LIMIT`.
- `index.IdList` (package-private): `jsonStrings(Collection<String>)` (JSON string array for `json_each`, escapes
  `"`, `\`, control chars) and `subsequencePattern(text)` (escaped `%a%b%` LIKE pattern); `containsPattern` now
  shares the escaping helper.
- `lookup.FindService`: patterns with an upper-case letter (`NamePattern.usesCamelHumps()`) take the hump path:
  `listNames(scope, ASCII chars of the pattern)` → `NamePattern.match` in memory → names sorted by score then name →
  `findByNames` in batches of 500 names, best names first, until `MEMBER_SCAN_LIMIT` (5,000) rows. All-lower-case
  patterns keep the substring path unchanged. Ranking/output unchanged.

## Decisions
- Approach chosen by measuring on the real JDK 25 index (7.6k types, 64.6k members, 22.8k distinct names) on a
  machine under load (load avg 10–15 from other agents; min of 10 runs):
  - unfiltered `SELECT DISTINCT name` in scope: 50–80 ms alone, `find` of a hump pattern ≈ 95–130 ms;
  - an extra covering index `(type_id, name)` only gained ~10 ms (and needs a schema bump) — rejected;
  - **subsequence `LIKE` pre-filter** (chosen): listing ≈ 22 ms; `find` `gFB` 47 ms, `HSR` 51, `MaP` 58, `oET` 83
    (broad: many names contain o…e…t), vs. substring path `getOr` 56, `map` 35. So hump patterns now cost about the
    same as the existing substring path.
- Why a subsequence is a safe superset: every exact/prefix/substring/hump match contains the pattern's characters in
  order (case-insensitively). A first-character prefix filter is *not* a superset (`SR` hump-matches
  `HttpServletRequest`), so it was not used.
- Non-ASCII pattern characters are dropped from the SQL filter (SQLite `LIKE` folds ASCII case only), so the filter
  stays a superset of Java's Unicode case-insensitive match. Remaining corner: a name containing a non-ASCII char that
  lower-cases to an ASCII letter (e.g. KELVIN SIGN) is not found by an ASCII pattern — the same limitation as T03's
  substring search.
- `truncated` is still set when the member row cap is reached; because hump rows are read best-name-first, the cap
  drops the weakest matches.
- No schema change.
