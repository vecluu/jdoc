# T06 notes — decompile (Vineflower + decompiled-source cache)

Status: done, `./mvnw -B -q -Djdoc.buildDir=target/T06 verify` passes. Package `io.github.vecluu.jdoc.decompile`.

## Public API
- `Decompiler` (interface) — `String decompile(Path jar, TypeName type)`: source of the **top-level** type
  enclosing `type` (nested binary names select their outermost type), nested/inner/anonymous classes included.
- `VineflowerDecompiler implements Decompiler` — stateless, thread-safe per call, Vineflower 1.12 in-process via
  `BaseDecompiler`. Feeds only `Outer.class` + `Outer$*.class` (same package dir) from memory; the jar itself is a
  *lazy* library (classes loaded on demand for reference resolution, never listed or decompiled).
- `DecompiledSourceProvider` (interface) — `String source(Gav gav, Path jar, TypeName type)`. **T09 should depend on
  this** (fake it in tests).
- `DecompiledSourceCache implements DecompiledSourceProvider` — `(CachePaths, Decompiler)`; `cacheFile(gav, type)`
  = `CachePaths.decompiledSource(gav, type.topLevel())` (`decompiled/<g>/<a>/<v>/<pkg>/<Outer>.java`); hit → read
  file, miss → decompile, write temp file in the same directory, `ATOMIC_MOVE` into place (fallback plain
  replace). Never called for JDK types.
- `DecompilationException extends JdocException` — jar unreadable / not a zip, no `Outer.class` entry, corrupt class,
  Vineflower failure. Message always starts with `Cannot decompile <display name>: ...`.
- Cache I/O failures are `CacheIoException` (T01).

Package-private helpers: `SelectedClassesSource` (in-memory `IContextSource` + output sink capturing the
top-level class text), `JarLibrarySource` (lazy ZipFile-backed library), `Slf4jFernflowerLogger` (all Vineflower
messages → slf4j debug; remembers whole-class failures, which Vineflower otherwise only emits as a
`// $VF: Couldn't be decompiled` comment).

## Output format (Vineflower options)
Generic signatures on, LVT names + MethodParameters names on, bridge/synthetic removed, enums/inner classes
decompiled, no banner, no decompiler comments, no bytecode/exception dumps, `\n` line ends, 4-space indent,
`thread-count=1` (deterministic). `include-runtime` left at its default (current JRT as lazy library) for better
type resolution. Output starts with `package ...;` and parses with `JavacTask.parse()` (verified in the IT).
Example: `record Point(int x, int y)`, field accesses rendered as `this.x`, varargs as `double... values`.

## Decisions / deviations
- Whole-class failure detection matches Vineflower's log message "couldn't be fully decompiled" (ERROR with
  throwable). Individual method failures are tolerated (output stays usable; a placeholder body is emitted).
- Racing processes may both decompile the same type; the last atomic move wins with identical content. No lock
  is taken (the index lock is for indexing only).
- `DecompiledSourceCache` does not validate the cached file against the jar's mtime: the path contains the
  version, and release jars are immutable. SNAPSHOT jars that change keep stale decompiled text — follow-up
  for T08/T09 if needed (e.g. delete `decompiledDirectory(gav)` when a snapshot jar is re-indexed).
