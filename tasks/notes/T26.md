## Root cause (evidence)
The brief's diagnosis, that the training-library generator failed, was wrong. It was inferred from the missing
"trained on the JDK and the training library" line, and the IT never showed the installer's stderr. That line is
also missing when the **whole AOT training** fails, and that is what happened:
- `coredumpctl` has exactly one java crash on this machine: Mon 2026-11-02 02:51:23, the installer's
  `java ... -XX:AOTMode=create -XX:AOTConfiguration=/tmp/junit-5862841331587337703/install-tmp/jdoc-install.*/jdoc.aotconf
  -XX:AOTCache=/tmp/junit-.../pre fix/lib/jdoc.aot.tmp` (an InstallerIT run during the orchestrator's verify, minutes
  after the T25 commit), SIGABRT from HotSpot's error handler after a SIGSEGV.
- gdb on the core: crashing frame `ArchiveBuilder::make_training_data_shareable()` (called by
  `VM_PopulateDumpSharedSpace::doit`), `mov 0x40(%rbx),%rdi` with `rbx = 0x800`, i.e. a corrupt node while it
  iterates the archive's source-object table to strip the training data (JEP 515 profiles). JDK: Microsoft
  OpenJDK 25.0.5.0.2. Similar JDK 25 bugs exist (JDK-8366948 "AOT cache creation crashes when iterating training
  data", JDK-8360164, JDK-8358680), all marked fixed in earlier 25.0.x builds, so this is a JVM bug that is still
  there or a new one. It is not in jdoc's code and has nothing to do with load, timeouts, temp files or locale.
- The installer's reaction was correct: AOT step failed, so it warned, printed the log tail, and exited 0. The IT's
  `contains` assertion failed without showing that stderr.
- The generator itself is deterministic: no threads, no timeouts, no network, fixed inputs. It does not depend on
  `java.io.tmpdir`, `user.home`, cwd or `TMPDIR` (each fault-injected: exit 0).

## Fix (`dist/install.sh`)
- `train_cache [extra flags]`: one attempt = fresh `JDOC_CACHE`, record, create, cache non-empty. If the first attempt
  fails, the installer retries **once** with a fresh recording and `-XX:+UnlockDiagnosticVMOptions
  -XX:-AOTRecordTraining`. A crash depends on one recording, so a new recording gets past it. The retry also leaves out
  the training data that the crashing code was processing, so it does not take that code path at all.
  It prints one stdout line, `install.sh: AOT training failed (<reason>); retrying once without method profiles`.
  Cost of the retry cache: 2-3 ms per lookup (measured, 40 interleaved rounds, `-XX:AOTMode=on`: `method` 91.7 vs
  94.7 ms, `class` 110.2 vs 111.9, `find` 124.0 vs 126.4, `--version` the same). The cache is 2.8 MB smaller. The
  first attempt keeps the training data. No timeouts were changed.
- Visibility: `first_error <log>` picks the line that names the error: `error:` (generator, jdoc), a JVM crash's
  `#  SIGSEGV (0xb) at pc=...` / `#  Internal Error`, an exception, else the first line. The generator fallback is now
  one stderr line, `install.sh: warning: could not generate the training library (<reason>); the AOT cache covers
  JDK lookups only`, with exit 0 as before. If both training attempts fail, the warning includes the reason
  ("failed twice (<reason>)") followed by the log tail as before.
- `TrainingLibrary` is unchanged (it was not at fault).

## Tests (`InstallerIT`, now 4: 3 install tests + shellcheck)
- Success test: the `contains("trained on ... training library")` assertion now prints the installer's
  stdout and stderr, so a future failure shows its reason.
- `installerWarnsWithTheReasonAndTrainsOnTheJdkWhenTheTrainingLibraryCannotBeGenerated`: a fake JDK home first on
  PATH, whose `bin/java` script fails only for the generator's main class (with two stderr lines) and execs the real
  java otherwise. Other entries are symlinks, deleted before `@TempDir` cleanup. Asserts exit 0, "trained on the
  JDK)", stderr exactly the one warning line with the first error line, and the cache and key exist.
- `installerRetriesTheTrainingOnceWhenTheJvmCrashesCreatingTheCache`: the fake `java` crashes the first
  `-XX:AOTMode=create` with an hs_err-like banner and exit 134. Asserts the retry line with the SIGSEGV reason, "trained on
  the JDK and the training library", empty stderr, and that the real java maps the cache with `-XX:AOTMode=on`.
- shellcheck is still not installed locally (test skipped). Scripts were written to its conventions (SC2086
  directive on the moved `$jvm_flags` line). `bash -n` passes.
