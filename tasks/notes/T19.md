## Answers to the outline's open questions
- **Sibling modules.** `mvn -o dependency:list` inside `b` fails while sibling `a` is not installed
  (`Could not resolve dependencies ... demo.t19:a:jar:1.0-SNAPSHOT`). **The old retry `-pl b -am` from the root failed
  too**: Maven 3 hands out a sibling's `target/classes` only if the lifecycle reaches `compile` (`test-compile` for
  `test-jar` siblings). `-pl b` without `-am` fails as well, even when `a/target/classes` exists. What works:
  `mvn -o -q -B test-compile dependency:list ... -Dmaven.main.skip=true -Dmaven.test.skip=true
  -Dmaven.resources.skip=true -pl b -am`. It compiles nothing and creates no `target/`. `a` is listed with its
  `target/classes` path and dropped as a reactor module, and `a`'s transitive deps (asm) are kept. Downside: plugins
  bound to phases up to `test-compile` (generators, enforcer, remote-resources) still run, and they must be available
  offline. Tested with Maven 3.10.0.
- **Resolution time.** Times are wall clock, offline, with a warm `~/.m2`. On jdoc itself (19 deps):
  `dependency:list` takes 1.5–1.6 s, and a cold `jdoc class` with the index already warm takes 1.73 s, then 0.24 s
  on a hit. Multi-module `b` via the reactor command: 1.7–1.9 s for Maven, 2.0 s for a cold jdoc call, then 0.28 s.
  A failing plain run costs about 1.3 s, which is why a module that declares a sibling now goes to the reactor
  directly. Conclusion: no git hook needed at this size.
- **Old javadoc jars.** `~/.m2` had none, so I downloaded `commons-lang3:3.5` + its `-javadoc` jar (built by JDK
  1.8.0_102, HTML 4.01) into `~/.m2` for this check and used it without a sources jar. Results: StringUtils 214/214
  members and ArrayUtils 307/307 have matched docs; `@param`/`@return`/`@since`, lists and `<pre>` blocks are
  rendered. Gap: signatures show `arg0`, `arg1` (class files without `-parameters`), while the docs use the real
  names. The parameter names could be taken from the javadoc HTML (javadoc/indexer follow-up, not done).

## Bugs found and fixed (`module`)
1. Reactor retry could never succeed (see above). `MavenDependencyLister` now runs the reactor command with
   `test-compile` + skip flags (`REACTOR_ARGUMENTS`). The resolver passes `reactorFirst` when the module or its local
   parents declare a dependency on a reactor module, which saves the failing ~1.3 s run. Otherwise it is plain first,
   then the reactor command.
2. Offline plugin prefix: with a pre-filled repo that has the plugin jar but not
   `org/apache/maven/plugins/maven-metadata-<repoId>.xml` (seen here before metadata was fetched), every run failed
   with `No plugin found for prefix 'dependency'`. New `DependencyPluginLocator` (newest local
   `maven-dependency-plugin` version with a jar). On that error the lister retries with
   `org.apache.maven.plugins:maven-dependency-plugin:<v>:list` and keeps that goal for the reactor attempt.
- Parser confirmed against real output: plugin 3.7.0 writes a leading blank line and 3.11.0 does not.
  `-- module x [auto]`, `test-jar` types and reactor directory paths are all handled. `-q -B` print nothing on
  success, and `-DoutputFile` with an absolute path works, also with `-am` (the target module writes last).
