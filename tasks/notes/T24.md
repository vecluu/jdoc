# T24 notes — skill design: when is jdoc worth calling?

Status: done. Docs only, no Java changes, no build/test impact. Checked against `java -jar target/T24/jdoc.jar --help`
and every `<command> --help` (T24 build), and ran the skill's commands in `it/sample-project` with a temp
`JDOC_CACHE`. Warm call 0.22 s, first call in a module ~6 s (index). Typical answer sizes: `find`/`member` 50-200 tokens,
one `method` ~250, `class Optional` ~840, `method java.util.List#of` (all overloads) ~1,400.

## Decision
The build is the primary verifier for signatures. jdoc is for what the model does not know, the step after the first
compile error ("never guess twice"), and behaviour the compiler cannot check.
Triggers: unfamiliar library or version (internal, niche, new major); name unknown (`find`/`member`); compile
error on a library symbol; behaviour (null, exceptions, mutability, thread safety, defaults, deprecation); the urge
to unzip/decompile. Skip: common JDK APIs in their usual form, calls the project already makes (grep instead),
anything already looked up this session.

## Dropped from the T18 version, and why
- "Before writing a call ... you have not verified in this session" (description and first bullet): over-triggers on
  every line that touches the JDK.
- "Exploring an unfamiliar type: `class` first, then `method` for the members you will use": replaced by "one `class`,
  not several `method` calls". The class page already shows signatures plus first sentences.
- Nothing harm-related was dropped: exit codes 1/2/3, no unzip/decompile, public/protected only, `--from`,
  `[version unresolved]`, `[decompiled, no docs]`, paging, `index --force`, `--help` all stay.
- Added: chaining several lookups in one shell call (saves turns; misses print `no member ...`/`no type ...` on
  stdout, so the output stays readable), parameters only for heavily overloaded methods, first-call index latency.

## Examples and T22
The examples quote commands and compiler messages only, no jdoc signature output, so T22's rendering changes
(no implicit `abstract`, real parameter names, find ranking) cannot make them stale.
