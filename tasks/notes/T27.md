## Changes
- `pom.xml` (release build settings only): `project.build.outputTimestamp` = `2026-01-01T00:00:00Z` for development
  builds, and profile `source-date-epoch`, active when the env var `SOURCE_DATE_EPOCH` is set, which uses it (epoch
  seconds) instead. One variable now fixes both the jar entries and the tarball entries (`assemble.sh` already used
  it). Default `revision` stays `0.0.0-SNAPSHOT`. jar-plugin 3.4.2 and shade 3.6.2 both honour it; entries copied from
  dependency jars keep their own (fixed) timestamps.
- `CHANGELOG.md` (new, Keep a Changelog): `[Unreleased]` + `[0.1.0] - 2026-11-02` with Added (commands, offline
  resolution, doc-source fallback, index/refresh, AOT startup, installer/bundle/provenance, skill) and a
  `### Known limitations` subsection (not a standard Keep a Changelog type; chosen deliberately): Linux/Java 25,
  aarch64 untested, Maven only, Java sources only, options after the command, weak fallback CDS archive, the JDK 25
  AOT crash + retry.
- `scripts/release-notes.sh <version>` (new): prints the CHANGELOG section (fails if missing/empty) plus an install
  footer (`gh release download`, `gh attestation verify`, `sha256sum -c`, install). Covered by shellcheck in CI via
  InstallerIT (`scripts/*.sh`).
- `.github/workflows/build.yml`:
  - Version step (`id: version`): sets `SOURCE_DATE_EPOCH` = commit time in `GITHUB_ENV` (used by Maven and
    assemble), exports `version` as a job output, and on tags/dry runs runs `release-notes.sh` first, so a missing
    changelog section fails in seconds instead of after the 4-minute build.
  - `workflow_dispatch` input `release-dry-run` (a version): the build job builds that version instead of
    `0.0.0-<sha>`, and the release job runs too but skips `actions/attest` and `gh release create` (prints the
    command). Attestations go to the public Sigstore log, so they are skipped as well.
  - Release job: checkout (for the script; `persist-credentials: false`); `download-artifact` with
    `pattern: jdoc-*` (before: all artifacts of the run, which would upload anything else as a release asset);
    a check that `out/` holds exactly `SHA256SUMS` + `jdoc-$VERSION.tar.gz` and that `sha256sum -c` passes; attest
    exactly the tarball; `gh release create v$VERSION <tarball> SHA256SUMS --verify-tag --title "jdoc $VERSION"
    --notes-file <changelog section>` (was `--generate-notes`, i.e. the gitmoji commit list) plus `--prerelease`
    for versions with `-`, and a tag/version equality guard.
- `README.md`: names 0.1.0 as latest and links the changelog; adds `gh release download v<version>`; the release
  steps start with `export SOURCE_DATE_EPOCH=...`; a reproducibility paragraph; the CI paragraph names the changelog
  notes and the dry run.

- CI vs CI (Temurin 25, ubuntu-24.04), two independent dispatch runs of d15d3c6: tarball
  `78ea69d45156bed5cb4fb3bc8bb3bd217e21087b0ccfd4e643b09264e45a462d` both times.
- Local vs CI for the same commit: tarball `5a079d17…` vs `78ea69d4…`. The jars have the same entry names, contents
  and timestamps; only the deflate bytes differ (1,347 compressed sizes, jar 15.48 MB vs 15.25 MB). Cause: this

  of the toolchain, not of the build, so I kept it as a documented caveat in the README rather than a fix.
  Independent rebuilds must use the CI toolchain.

## Hand-off (after the user's explicit approval only)
Run from the repo root on `main`. `$SHA` is the commit to release, i.e. `main` after the T27 commits.
1. Commit T27 (scoped commits below), push `main`, and wait until CI on that commit is green:
   `git push origin main`, then `gh run list -R vecluu/jdoc --workflow build.yml --branch main --limit 1`.
   `SHA=$(git rev-parse HEAD)`, and check `git status --short` is empty and `git rev-parse origin/main` equals `$SHA`.
2. Optional, but recommended. Run a dry run on that commit; nothing is published:
   `gh workflow run build.yml -R vecluu/jdoc --ref main -f release-dry-run=0.1.0`, then
   `gh run watch <id> -R vecluu/jdoc --exit-status` and keep its `SHA256SUMS`
   (`gh run download <id> -R vecluu/jdoc -D /tmp/jdoc-dry`). The tag build should give the same checksum.
3. If the release is not on 2026-11-02, fix the `[0.1.0]` date in `CHANGELOG.md` first (new commit, back to 1).
4. Tag and push (after the user's explicit approval only):
   `git tag -a v0.1.0 -m "jdoc 0.1.0" "$SHA"` and then `git push origin v0.1.0`.
5. Watch the run: `RUN=$(gh run list -R vecluu/jdoc --workflow build.yml --event push --branch v0.1.0 --limit 1
   --json databaseId --jq '.[0].databaseId')`, then `gh run watch "$RUN" -R vecluu/jdoc --exit-status`.
   Both the build and the release jobs must succeed.
6. Verify the published assets in a temp dir:
   `D=$(mktemp -d) && cd "$D" && gh release view v0.1.0 -R vecluu/jdoc` (expect title "jdoc 0.1.0", not a
   prerelease, notes = CHANGELOG section + install footer, 2 assets). Then
   `gh release download v0.1.0 -R vecluu/jdoc && sha256sum -c SHA256SUMS` and
   `gh attestation verify jdoc-0.1.0.tar.gz -R vecluu/jdoc`. Also compare `SHA256SUMS` with the dry run's from step 2.
7. Install into a temp prefix:
   `tar xzf jdoc-0.1.0.tar.gz && ./jdoc-0.1.0/install.sh --prefix "$D/prefix" --bindir "$D/bin" --skills-dir "$D/skills"`.
   Then `JDOC_CACHE="$D/cache" "$D/bin/jdoc" --version` must print `jdoc 0.1.0`.
   For the full check, from the repo with Maven on PATH:
   `scripts/install-test.sh "$D/jdoc-0.1.0.tar.gz" it/sample-project`.
8. Finally, check that the README badge is green on `main`, and that the releases page shows 0.1.0 as Latest.
If the build job fails, no release exists. Fix it on `main`, then (with approval) delete and recreate the tag with
`git push origin :refs/tags/v0.1.0` and `git tag -d v0.1.0`. If only `gh release create` failed after the attestation,
rerun the failed job: `gh run rerun "$RUN" -R vecluu/jdoc --failed`.
